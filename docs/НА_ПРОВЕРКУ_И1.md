## 1. БЛОКЕР И1-A: ВРЕМЯ

### Что было

`trade_manager._история_после()`:

```python
начало = datetime.fromtimestamp(момент_сервера - 5.0)
```

`datetime.fromtimestamp()` без аргумента `tz` строит **наивное местное**
время машины. Терминал MetaTrader 5 отдаёт метки времени в UTC и запросы
трактует как UTC.

### Чем это било

Ровно тем сценарием, ради которого сверка и написана.

1. `order_send` вернул `TIMEOUT` — ответа нет.
2. Позиция успела открыться и тут же закрыться по стопу.
3. Среди открытых позиций её нет, значит ищем в истории.
4. На машине в UTC−6 окно запроса уезжало на **шесть часов назад**.
5. История возвращалась пустой.
6. Программа делала вывод **«сделка не открылась»** и шла торговать дальше.

Отдельно неприятное свойство: **на машине с часами в UTC дефект не
проявляется вовсе**. Местное время и UTC совпадают, и неверный код
выглядит верным. Поэтому тест обязан переставлять часовой пояс.

### Что стало

`trade_manager._история_после()`:

```python
секунды = max(0.0, float(момент_сервера) - ОКНО_ИСТОРИИ_НАЗАД)
начало = datetime.fromtimestamp(секунды, tz=_tz.utc)
конец = начало + timedelta(seconds=ОКНО_ИСТОРИИ_НАЗАД + ОКНО_ИСТОРИИ_ВПЕРЁД)
```

Плюс вторая линия обороны в `mt5_connector.deals_or_none()`: любое
наивное время достраивается до UTC перед передачей в терминал, чтобы
ошибка не вернулась через другой вызов.

```python
def _в_utc(момент):
    """datetime без часового пояса считается UTC, а не местным временем."""
    if isinstance(момент, datetime) and момент.tzinfo is None:
        return момент.replace(tzinfo=timezone.utc)
    return момент
```

Окно сужено: было −5 с … +1 час, стало **−5 с … +10 минут**. Чем шире
окно, тем больше в него попадёт чужих сделок, а каждая лишняя делает
ответ неоднозначным.

### Как это проверено

**Т14** переставляет часовой пояс процесса на `Etc/GMT+6` (UTC−6),
кладёт сделку в историю в правильной UTC-точке и требует, чтобы сверка
её нашла.

**Проверка «наоборот».** Со старой строкой (`fromtimestamp` без `tz`)
тест падает:

```
СБОЙ  И окно накрывает момент сделки по времени СЕРВЕРА
      -> окно 1699978395.0..1699979000.0, сделка 1700000001.0
СБОЙ  Окно не уехало на разницу часовых поясов
      -> начало 1699978395.0, ожидалось 1699999995.0
СБОЙ  Сделка найдена в истории — торговля ОСТАНОВЛЕНА, а не «отказ»
```

Смещение `1699999995 − 1699978395 = 21600` секунд — ровно шесть часов.

### Замечание к методике теста

Подделка `history_deals_get` в тесте **специально воспроизводит трактовку
времени терминалом**: наивный `datetime` считается UTC, а не местным
временем.

Без этой модели дефект не проявился бы вообще: `fromtimestamp(ts)` и
последующий `.timestamp()` свернулись бы обратно в исходный `ts`, и тест
был бы зелёным при сломанном коде. Это отмечено комментарием в самой
подделке.

## 2. БЛОКЕР И1-B: ПРИВЯЗКА К ЗАЯВКЕ

### Что было

Широкое окно, фильтр только по трём признакам — инструмент, `magic`,
«это вход», — после чего **объёмы всех найденных сделок складывались**:

```python
входы = [d for d in сделки
         if int(getattr(d, "position_id", 0) or 0) not in снимок]
if входы:
    объём = sum(float(getattr(d, "volume", 0.0) or 0.0) for d in входы)
```

Такой фильтр не отличает нашу заявку от чужой. Второй экземпляр программы
с тем же `magic`, или сделка, открытая руками в терминале, попадают в то
же окно и выглядят точно так же. Сложить их объёмы — соврать про размер
позиции на счету.

### Что стало

Три уровня, от строгого к слабому.

**Уровень 1 — по номеру ордера.** Единственная строгая связь между
историей и нашей заявкой:

```python
if подсказка_тикет and подсказка_тикет > 0:
    по_номеру = mt5c.deals_by_order(подсказка_тикет)
    if по_номеру is None:
        return ex.неизвестно(
            f"ответ брокера неясен, историю по ордеру "
            f"{подсказка_тикет} прочитать не удалось", заказано)
    входы = [d for d in по_номеру
             if int(getattr(d, "entry", -1)) == mt5c.DEAL_ENTRY_IN]
    if входы:
        объём = sum(_объём_сделки(d) for d in входы)
        return ex.неизвестно(
            f"позиция по ордеру {подсказка_тикет} открывалась "
            f"(объём {объём:.2f}) и уже закрыта — нужен человек, "
            f"автоматика такое не разбирает", заказано)
```

Номер ордера берётся из `result.order` разобранного ответа и передаётся в
сверку параметром `подсказка_тикет`.

**Уровень 2 — строгое соответствие.** Если номера нет: инструмент,
`magic`, «это вход», **направление сделки** (`DEAL_TYPE_BUY` для лонга,
`DEAL_TYPE_SELL` для шорта — этого фильтра раньше не было) и узкое окно.

**Уровень 3 — запрет угадывания:**

```python
if len(кандидаты) > 1:
    return ex.неизвестно(
        f"в истории за это окно несколько подходящих сделок "
        f"({len(кандидаты)}) — какая из них наша, определить нечем",
        заказано)
```

Ни сложения объёмов, ни выбора «самого свежего».

**То же правило для открытых позиций.** Если после неясного ответа
появилось несколько новых позиций нужного направления, а номер ордера
неизвестен, — это `НЕИЗВЕСТНО` и остановка:

```python
if len(новые) > 1:
    номера = ", ".join(str(p.ticket) for p in новые)
    return ex.неизвестно(
        f"после неясного ответа появилось несколько новых позиций "
        f"({номера}) — какая из них наша, определить нечем", заказано)
```

Когда номер ордера известен, неоднозначности не возникает: наша позиция
определяется по номеру, и чужая рядом ничему не мешает. Это отдельно
проверяется (Т17).

### Как это проверено

**Проверка «наоборот».** С отключёнными правилами (поиск по номеру
ордера выключен, проверка `len(кандидаты) > 1` выключена) падают Т16 и
Т17:

```
СБОЙ  И в сообщении назван номер ордера
      -> ...(объём 0.06)...   номера ордера в сообщении нет
СБОЙ  И сказано, что кандидатов несколько
      -> ...(объём 0.03)...   выбран первый попавшийся
```

## 4. ПОЛНАЯ ТЕСТ-МАТРИЦА И1

Первая часть работы (ревизия `8da6f4d`), проверяется по-прежнему:

| № | Сценарий | Проверяется по факту |
|---|---|---|
| 1 | Частичное исполнение **первой** ноги хеджа | вторая нога не отправлена, **счёт пуст** |
| 2 | Полная первая нога, **частичная вторая** | закрыты **обе**, **счёт пуст** |
| 3 | Обе ноги целиком *(контроль)* | ничего не закрыто, два равных объёма |
| 4 | Частичное компенсационное закрытие | остаток дозакрыт, **счёт пуст**, паузы нет |
| 5 | Остаток дозакрыть не удалось | **остаток виден на счету**, торговля остановлена |
| 6 | Дозакрытие ограничено | не больше трёх попыток |
| 7 | `TIMEOUT`, позиция открылась | одна заявка, **одна позиция, не две** |
| 8 | `TIMEOUT`, позиция не открылась | счёт пуст, паузы нет, повтора нет |
| 9 | `TIMEOUT` + терминал не отвечает | остановка; вслепую ничего не открыто и не закрыто |
| 10 | Неясный ответ на **вторую** ногу | остановка + в сообщении сказано, что первая уже открыта |
| 11 | После неясного ответа нет повтора | ровно одна заявка при включённых повторах |
| 12 | Реквот повторяется *(контроль)* | вторая попытка есть, сделка открыта |
| 13 | Одиночная сделка исполнена частью | позиция **жива**, объём ровно половина заказанного |
| 14 | Расхождение объёмов в журнале | событие записано |
| 15 | `DONE` с урезанным объёмом | считается частичным |
| 16 | `DONE` с нулевым полем объёма | считается полным |
| 17 | `DONE_PARTIAL` без объёма | `НЕИЗВЕСТНО`, не ноль |
| 18 | Нечитаемый код ответа | `НЕИЗВЕСТНО`, а не падение торгового цикла |
| 19 | `bool(итог)` | `TypeError` с объяснением |
| 20 | Числа кодов совпадают с терминалом | пять констант сверены |
| 21 | Частичная фиксация прибыли | не режет сделку по кругу |
| 22–25 | Бронь: отказ / неясно / успех / частично | нет / нет + остановка / есть / есть |

Плюс Т14–Т17 и «+1» из раздела 3.

### Чего эти тесты НЕ проверяют

* перезапуск программы во время остановки — это **И2**;
* сверку состояния при старте — это **И3**;
* поведение у настоящего брокера на живом счёте.
