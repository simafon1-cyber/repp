## 1. ДЕФЕКТ ПОДТВЕРЖДЁН ДОСЛОВНО

Аудит указал на обратный обход новой логики в самом начале
`сверить_вход()`. Код на ревизии `703c279`:

```python
новые = [p for p in позиции
         if int(p.ticket) not in снимок and p.type == нужный_тип]

if подсказка_тикет and подсказка_тикет > 0:
    точная = next((p for p in новые
                   if int(p.ticket) == int(подсказка_тикет)), None)
    if точная is not None:
        новые = [точная]

if len(новые) > 1:
    return ex.неизвестно(...)

if новые:
    нашлась = новые[0]        # ← ЗДЕСЬ
    ...
    return ex.Итог(статус, int(нашлась.ticket), ...)
```

Ключ в строке `if точная is not None`. Если номер заявки известен, **но
позиции с таким номером среди новых нет**, список `новые` **не
очищается**. Единственная чужая позиция проходит дальше и принимается за
результат нашей заявки.

### Сценарий вреда

1. Отправлена заявка **A**, ответ неясен, но `result.order = A` известен.
2. В этот же момент другой процесс с тем же `magic`, инструментом и
   направлением открыл позицию **B**.
3. Заявка A жива на сервере — её видно в `orders_get(ticket=A)`.
4. Код видит одну новую позицию B, принимает её за A, возвращает успех и
   **не ставит паузу**.
5. Потом исполняется A. На счету две позиции, одна из них не учтена.

Это нарушало два собственных правила проекта: И1-B «ничего не угадывать»
и И1-C «не считать заявку разрешённой, пока нет доказательства».

## 2. ЧТО СТАЛО

Совпадение по инструменту, направлению и «она тут одна» — это **приметы,
а не связь**. Настоящая связь существует ровно одна:

```
ЗАЯВКА  →  СДЕЛКА ВХОДА  →  НОМЕР ПОЗИЦИИ
```

`сверить_вход()` теперь начинается не с осмотра позиций, а с развилки по
главному признаку: известен ли номер заявки.

### 2.1. Номер известен — приметы не участвуют вовсе

`_разобрать_по_номеру()` задаёт вопросы по порядку:

| Шаг | Что спрашивается | Ответ | Итог |
|---|---|---|---|
| 1 | сделки **по этому номеру заявки** | сделки указывают на разные позиции | `НЕИЗВЕСТНО` |
| | | позиции с этим номером среди открытых нет | `НЕИЗВЕСТНО` — её уже закрыли |
| | | позиция найдена по номеру из сделки | **`ПОЛНОЕ` / `ЧАСТИЧНОЕ`** |
| 2 | жива ли заявка сейчас | да | `НЕИЗВЕСТНО` |
| 3 | чем закончилась | отменена / отклонена / истекла, сделок нет | **`ОТКАЗ`** |
| | | исполнена, но сделки не видно | `НЕИЗВЕСТНО` |
| | | не найдена нигде | `НЕИЗВЕСТНО` |
| любой | запрос не прошёл | | `НЕИЗВЕСТНО` |

Позиция принимается за нашу **только** по номеру, полученному из сделки
по нашей заявке. Инструмент, направление и «она одна» здесь не
спрашиваются ни разу.

**Объём берётся из сделок, а не из позиции.** Это важно для неттинговых
счетов, где заявка добавляет объём к уже существующей позиции: там
`p.volume` — это не наш объём, а суммарный.

### 2.2. Номера нет — связь не проследить в принципе

Здесь у сервера нечего спросить: ни найти заявку среди активных, ни
узнать её исход, ни проследить цепочку. Итог всегда `НЕИЗВЕСТНО`.

Появившаяся рядом позиция **больше не засчитывается**. Сообщение говорит
прямо: «Похожи на нашу, но доказать это нечем: без номера заявки связь не
проследить».

## 3. ГДЕ Я ПОШЁЛ ЗА БУКВУ ЗАДАНИЯ

Раздел «Требуемое исправление И1-D» описывает порядок для случая
`подсказка_тикет > 0`. Я применил то же правило и к случаю **без номера**:
появившаяся позиция больше не засчитывается.

Обоснование — пункт 6 самого задания: «Если API/брокер не позволяет
установить связь order → deal → position, безопасный результат —
НЕИЗВЕСТНО, а не выбор похожей позиции». Без номера связь не
устанавливается **никогда**, а механизм вреда тот же самый: чужая позиция
засчитывается вместо нашей, наша исполняется позже, экспозиция не учтена.

**Цена этого решения названа прямо.** Изменился ранее принятый тест Т7:
`TIMEOUT`, после которого позиция появилась, теперь засчитывается **только
если прослежена цепочка**. Раньше хватало появления позиции.

Если проверяющий считает такое расширение неоправданным — прошу сказать,
я откачу его до буквы задания.

## 4. ИСПРАВЛЕНИЕ В САМОЙ ПОДДЕЛКЕ БРОКЕРА

При работе выяснилось, что подделка брокера **не записывала сделку** при
открытии позиции, тогда как настоящий терминал записывает всегда.

Это делало подделку **добрее настоящего брокера**: цепочку «заявка →
сделка → позиция» проследить было нельзя, и тест этого не замечал.
Подделка исправлена — теперь она пишет сделку на каждое открытие и
закрытие.

Отмечаю отдельно, потому что это ошибка в моей же тестовой основе, а не в
программе. Без неё Т23 был бы зелёным по неверной причине.

## 5. ТЕСТЫ

| Тест | Сценарий | Критерий | Итог |
|---|---|---|---|
| **Т22** | Заявка A жива; появилась ровно **одна чужая** позиция B того же инструмента / направления / `magic` | `НЕИЗВЕСТНО` + пауза; B **не** засчитана как A; оператору показан номер A; новой заявки нет | ✅ |
| **Т23** | У заявки A есть сделка входа с `position_id = P`, где **P ≠ A**; среди позиций есть P и чужая B | принята **только P** как результат A; B не тронута и ни на что не влияет | ✅ |
| **Т24** | Заявка A активна, позиция B появилась до её исполнения | после следующего обхода пауза сохраняется; A не забыта и не подменена B | ✅ |
| **Т17** *(расширен)* | Известен номер заявки; рядом чужая сделка **и чужая открытая позиция** | берётся только связанная; чужая позиция не тронута и не засчитана | ✅ |
| +1 | Сделки одной заявки указывают на **разные** позиции | `НЕИЗВЕСТНО` + пауза, выбор наугад запрещён | ✅ |
| +2 | Цепочка прослежена, а позиции с этим номером уже нет | `НЕИЗВЕСТНО` + пауза, назван номер прослеженной позиции | ✅ |
| +3 | **Структурная**: при известном номере приметы направления в коде не встречаются | `_тип_позиции` и `нужный_тип` отсутствуют в `_разобрать_по_номеру` | ✅ |

### Проверка «наоборот»

Вернул старый порядок (сначала поиск единственной новой позиции по
приметам). Падают три проверки, и сбой показывает **ровно тот вред**:

```
СБОЙ  ТОРГОВЛЯ ОСТАНОВЛЕНА
СБОЙ  Оператору показан номер НАШЕЙ заявки
      -> 'EURUSD: заказано 12.00 лота, исполнено 0.01.
          Позиция открыта и защищена стопом...'
СБОЙ  Причина названа -> 'OK (исполнено частично)'
```

Чужая позиция объёмом **0.01** засчитана как наша сделка на **12.00**,
программа сообщила «OK» и пошла дальше. Это и есть И1-D в одной строке.
