## 1. Как формируется score (этапы 1.1–1.5)

### Путь решения о входе

`main.process_symbol()` → примерно 20 запретов подряд → `se.calc_signal_score()`
для BUY и SELL отдельно → надбавки (AI, стратегия, своя стратегия,
мульти-индикатор) → сравнение с порогом → `execute_market_order`.

Окончательное решение принимается в `main.py`, строки ~608–630.

### Базовый score (`signal_engine.calc_signal_score`)

Портирован из `SignalEngine.mqh`, веса совпадают:

| Компонент | Баллы | Источник |
|---|---|---|
| Тренд старшего ТФ (EMA-стек + M15) | 20 | `ema_stack_ok`, `trend_direction_mtf` |
| Откат + пробой | 20 | `pullback_breakout_ok` |
| Price Action (тело/тень свечи) | 15 | `is_bullish/bearish_confirmation` |
| ATR к среднему | 10 | `df["atr"]` |
| ADX | 10 | `df["adx"]` |
| Спред | 5 | `mt5c.get_spread_points` |
| Объём | 10 | `tick_volume` (или 10 «даром», если фильтр выключен) |
| Время | 5 | **выдаётся всегда** — фильтра нет |
| RSI (запас хода) | 5 | `df["rsi"]` |

Далее: штраф за новость, поправка на режим рынка, поправка на

**Два жёстких вето внутри score** (возвращают 0.0, минуя всё остальное):

`AI_SIGNAL_WEIGHT=10`, `STRATEGY_SIGNAL_WEIGHT=12`, `CUSTOM_STRATEGY_WEIGHT=15`,
`MULTI_INDICATOR_WEIGHT=12`. Все четыре включены по умолчанию.

## 2. КРИТИЧНО-1: сдвиг на один бар

### Что найдено

`mt5_connector.get_rates_df` берёт бары так:

```python
rates = mt5.copy_rates_from_pos(symbol, tf, 0, count)
```

Позиция **0 в MetaTrader — это текущая, ещё формирующаяся свеча.** Значит
последняя строка датафрейма — незакрытая свеча.

При этом `indicators.pullback_breakout_ok` в собственной документации
утверждает обратное:

> «последняя строка = последняя ЗАКРЫТАЯ свеча (signal), предпоследняя =
> pullback»

А MQL5-оригинал, с которого всё портировано, задаёт это явно
(`ai_scalper_pro/Config.mqh`, строки 8–9):

```
#define SIGNAL_SHIFT 1   // анализируем последнюю ЗАКРЫТУЮ свечу, не текущую формирующуюся
#define PULLBACK_SHIFT 2 // свеча отката — на бар раньше сигнальной
```

**Python сдвинут на один бар относительно советника.** Сигнальной свечой он
считает формирующуюся, а свечой отката — последнюю закрытую.

### Почему это хуже, чем кажется

Вход разрешён только на новом баре (`is_new_bar` в `main.py`). Новый бар
определяется по смене времени последней строки — то есть **ровно в момент,
когда свеча только открылась**. Опрос идёт раз в 5 секунд. Значит решение
принимается по свече возрастом 0–5 секунд, у которой почти нулевой диапазон.

Последствия по компонентам:

| Компонент | Что происходит на пустой свече |
|---|---|
| **Price Action (жёсткое вето)** | `rng = high - low` ≈ 0. При `rng <= 0` возвращается False → **score = 0 и вход запрещён**. Иначе тело/тень — случайный шум |
| **Откат + пробой (20 баллов)** | `sig["high"] > pb["high"]` — свеча за 5 секунд почти никогда не перебивает максимум предыдущей → 20 баллов не начисляются практически никогда |
| **Фильтр истощения** | Диапазон ≈ 0 → **не срабатывает никогда** |
| **ATR (10 баллов)** | True Range пустой свечи ≈ 0 → сглаженный ATR занижен → занижен и стоп-лосс |
| **Режим рынка** | Голос ATR смещён в сторону «флэт» |
| **EMA / RSI / ADX** | Смещены на неполную свечу |

**Это наиболее вероятная настоящая причина жалобы «нету сделок».** Ранее я
объяснял её тем, что в Market Watch попали 497 американских акций. Та причина
была реальной и исправлена, но она не единственная: жёсткое вето по Price
Action на пустой свече закрывает вход независимо от списка пар.

Это **не** look-ahead bias. Это зеркальная ошибка: используется свеча, которой
ещё нет, вместо свечи, которая только что была.

### Отдельное следствие для проверки на истории

При прогоне по истории «последняя свеча» будет **полной**. То есть backtest и
живая торговля работают по разным правилам, и любые числа с истории были бы
завышены. **Пока это не исправлено, строить baseline бессмысленно.**

## 3. Look-ahead аудит (этап 3)

Проверено покомпонентно. **Использования будущих данных не найдено.**

| Компонент | Вывод |
|---|---|
| EMA, ATR, RSI, ADX, MACD, Bollinger, Stochastic | Только `shift(1)` назад и сглаживание. Заглядывания вперёд нет |
| Efficiency Ratio | Окно назад, `iloc[-(period+1):]` — чисто |
| Режим рынка | Считается по прошлым барам, смена подтверждается несколькими барами — чисто |
| **Обучение цели (MFE)** | **Проверено особо.** `record_trade_peak` вызывается при ЗАКРЫТИИ сделки, медиана берётся по УЖЕ ЗАКРЫТЫМ сделкам. Своё будущее сделка не видит — **look-ahead нет** |
| Подтяжка тейка | Использует пик прибыли САМОЙ сделки, но только уже достигнутый — это факт, а не будущее |
| Auto Learning | Окно прошлых результатов — чисто |
| Новости | Смотрит вперёд по календарю, но это **известное заранее расписание**, а не будущая цена — допустимо |
| AI | Получает только прошлые бары |
| Кэш AI | 60 секунд, `datetime.now()` — заглядывания нет |

**Единственная временная ошибка — противоположная**: сдвиг из раздела 2.

## 4. Конфликты и дублирование фильтров (этапы 1.4, 1.20, 6)

### Одна и та же информация учитывается многократно

| Исходный факт | Сколько раз входит в решение |
|---|---|
| **ADX** | 10 баллов в score + голос в режиме рынка + бонус/штраф режима (`REGIME_TREND_BONUS` / `REGIME_RANGE_PENALTY`) + через режим меняет адаптивные множители тренда и RSI + через режим меняет вес AI = **пять раз** |
| **ATR** | 10 баллов + голос режима + фильтр истощения + `volatility_ok` + ширина стопа + расчёт тейка = **шесть раз** |
| **EMA-тренд** | 20 баллов + `pullback_breakout_ok` + стратегии + momentum своей стратегии = **четыре раза** |
| **RSI** | 5 баллов + Stochastic в мульти-индикаторе (близкий по смыслу) + передаётся в AI = **три раза** |

Из девяти «независимых» компонентов реально независимых — от двух до трёх.
Score выглядит как взвешенная сумма разных мнений, а по сути это два-три
факта, посчитанных по нескольку раз.

### Score насыщается и глушит собственные надбавки

Максимум базового score: 20+20+15+10+10+5+10+5+5 = **ровно 100**. При
`USE_ADAPTIVE_SCORE_WEIGHTS=True` множитель тренда 1.15 поднимает потолок до
~106, плюс бонус за режим и контекст.

Дальше `calc_signal_score` **зажимает результат в 100**, и только потом
добавляются AI (±10), стратегия (+12), своя стратегия (±15) и
мульти-индикатор (±12).

**Итог: в сильном тренде — то есть именно тогда, когда сигнал лучше всего —
score уже равен 100, и все четыре надбавки не могут ничего изменить.** Они
работают только на слабых сигналах. Это ровно противоположно замыслу.

### Два фильтра противоречат друг другу

`BLOCK_ENTRY_IN_RANGE` полностью запрещает вход во флэте. Одновременно
`_adaptive_multiplier` усиливает вес RSI (возврат к среднему) в 1.6 раза
именно во флэте, а `effective_ai_weight` повышает вес AI в 1.3 раза тоже во
флэте. Обе настройки готовят систему к торговле во флэте, которая запрещена.

### Время — 5 баллов даром

`score += 5` с комментарием «жёсткого тайм-фильтра нет». Компонент не несёт
информации, но входит в шкалу и в порог. Фактически порог 45 — это порог 40.

Так же «даром» выдаются 10 баллов за объём, когда `USE_VOLUME_FILTER=False`.

## 5. Auto Learning (этап 9) — самый опасный узел

`AUTO_LEARNING_MIN_TRADES = 5`, `AUTO_LEARNING_WINDOW = 20`.

### Обратная связь есть, и она признаётся

Порог входа снижается после удачной серии (до −10) и повышается после
неудачной (до +15).

**Пять сделок — это не статистика.** Стандартная ошибка оценки винрейта на
пяти наблюдениях составляет около ±22 процентных пунктов. Три выигрыша из
пяти (60%) неотличимы от 40%, но система уже снижает порог входа. Дальше:
ниже порог → больше сделок → другой состав сделок → другой винрейт. Петля
замкнута.

### `adaptive_ai_weight_multiplier` приписывает AI чужой результат

Множитель веса AI считается по общему винрейту символа — **независимо от
того, участвовал ли AI в этих сделках и совпадал ли он с направлением.**
Если пара шла хорошо без AI, доверие к AI всё равно растёт в 1.5 раза. Связи
между измеряемым и изменяемым нет.

### Обучение цели может сжиматься само в себя

`learned_profit_points` = медиана пиков × `TP_LEARN_FRACTION`. Сделки,
закрытые по стопу, записывают пик 0 и тянут медиану вниз. Меньше цель →
раньше выход → меньше зафиксированные пики → ещё меньше цель. Спираль
ограничена только `TP_LEARN_MIN_POINTS`. Это **не** look-ahead, но требует
измерения.

### Что Auto Learning НЕ делает (проверено — хорошо)

Не трогает риск, лот, стоп-лосс, дневной лимит и лимит просадки.
Границы `AI_WEIGHT_MULT_MIN/MAX` и `SCORE_THRESHOLD_ADJUST_MIN/MAX`
соблюдаются. Требования этапа 9 в этой части выполнены.

## 6. AI (этапы 7, 8)

### Что проверено и хорошо

AI **не может**: открыть сделку, увеличить риск, увеличить лот, расширить
стоп, обойти Risk Manager, обойти дневной лимит и лимит просадки. Его влияние
— строго ±`AI_SIGNAL_WEIGHT` (10 баллов из 100) через `apply_ai_signal`,
результат зажат в 0..100. Требования этапа 7 в части полномочий выполнены.

При недоступности AI — `fail-open`: «neutral», уверенность 0, score не
меняется.

### Что не так

1. **`USE_AI_SIGNAL = True` по умолчанию.** Этап 7 требует не делать AI
   обязательным до A/B-сравнения. Сравнения не было.
2. **`AI_FAILURE_MODE` не существует.** Поведение при отказе AI зашито
   («считаем neutral») и не выбирается.
3. **Влияние AI почти всегда нулевое** — из-за насыщения score (раздел 4).
   То есть заплатить за AI-запросы можно, а повлиять он может только на
   слабые сигналы.
4. **Контекст беден**: 20 цен закрытия, RSI, ADX, максимум и минимум за 20
   баров. Нет старших таймфреймов, спреда, сессии, режима. Но по этапу 8
   расширять контекст **нельзя без измерения**, и я этого не предлагаю.
5. Расход растёт линейно с числом пар, а пар теперь десятки. При кэше 60 с и
   M5-барах это ощутимо.

## 7. Risk Manager (этап 11)

### Что сделано правильно

Объём считается от риска; проверяются `volume_min/max/step`; при
невозможности уложиться в риск сделка либо отменяется, либо громко
предупреждает; есть отдельный жёсткий потолок риска на сделку; есть дневной
лимит, лимит просадки, пауза после серии убытков; есть ограничение по валюте
(`MAX_POSITIONS_PER_CURRENCY = 3`).

### Расхождение Python и MQL5 (этап 1.16)

**`RiskManager.mqh:271`** использует `OrderCalcProfit` — точный расчёт самого
терминала, с запасным путём через `tick_value/tick_size`.

**`risk_manager.py:349`** использует **только** приближение:

```python
loss_per_lot = (sl_dist / info.trade_tick_size) * info.trade_tick_value
```

`mt5.order_calc_profit()` в Python-API существует и не используется. Для
инструментов с валютой прибыли, отличной от валюты счёта (золото, кроссы,
индексы), приближение расходится с реальностью. Именно на золоте у владельца
и был основной убыток.

**Не проверяются вовсе:** `SYMBOL_TRADE_STOPS_LEVEL` и `FreezeLevel`
запрашиваются в `check_stops_distance`, но `OrderCalcMargin` / проверка
свободной маржи в Python-версии отсутствуют.

### Защита просадки снимается перезапуском

`acc_state.peak_equity` и `sym_state.pause_until` живут только в памяти
процесса. Перезапуск обнуляет пик — и запрет по просадке исчезает. В коде это
честно описано, но **не исправлено**. Для «последнего рубежа защиты денег»
это дыра.

### Потолок риска в 20 раз выше цели

`MAX_TRADE_RISK_PERCENT_OF_EQUITY = 2.0` при `risk_percent` профилей
0.1–1.2%. На малом счёте, где минимальный лот брокера всё равно больше
расчётного, реальный риск определяет **потолок**, а не цель. То есть
настройка «риск 0.1%» на счёте $442 не работает; работает «до 2%».

### Портфельный риск (этап 12)

Ограничение по валюте есть, но считает **число позиций**, а не риск. Три
сделки против доллара по 2% — это одна ставка на 6%. Общий
`max_total_risk_pct` существует, но корреляцию не учитывает.

## 8. Хедж-режим — отдельное замечание

У профиля «Истеричка» (`hedge_both_directions`) при прохождении порога хоть
одной стороной открываются **обе** — BUY и SELL одновременно.

Направленного преимущества у такой конструкции нет по построению, а спред
платится дважды. Математическое ожидание такой пары сделок отрицательно на
величину двойного спреда плюс своп. Это следует либо измерить, либо
отключить.

## 13. План работ

### Шаг 1 — исправить сдвиг на один бар (CRITICAL)

Одна правка в месте получения баров: убрать формирующуюся свечу, чтобы
последняя строка была последней ЗАКРЫТОЙ — как `SIGNAL_SHIFT = 1` в MQL5.
Плюс тест, который прямо проверяет: сигнальная свеча закрыта, её время
не совпадает со временем текущего бара.

Ожидаемый эффект: **сделки начнут появляться**, а Price Action, откат+пробой
и фильтр истощения впервые заработают как задумано. Влияние на прибыль —
**UNKNOWN** до измерения.

### Шаг 2 — построить baseline (CRITICAL)

Написать связку «история баров → `signal_engine` → `backtest.simulate`»:
прогон существующей стратегии по скачанной истории без единого изменения
настроек. Плюс расчёт метрик, которых сейчас нет: Sharpe, Sortino, средний R,
MAE, MFE, максимальные серии, винрейт отдельно по BUY и SELL.

Данные для этого может дать сам MetaTrader на машине владельца.

### Шаг 3 — измерить каждый фильтр (этап 5)

Только после шагов 1–2. Для каждого компонента — прогон с ним и без него на
одних данных, метка HELPFUL / NEUTRAL / HARMFUL / UNKNOWN. Ничего не
включать и не выключать по итогам одного отрезка.

### Шаг 4 — Walk-forward

История режется на последовательные окна TRAIN → VALIDATION → OOS. Параметры
подбираются только на TRAIN, проверяются на VALIDATION, а OOS трогается
**один раз** и только для проверки. Механика уже написана и проверена:
`validation.py` (`windows`, `split_out_of_sample`, `walk_forward_check`,
`monte_carlo_check`, `ab_check`).

### Шаг 5 — точечные исправления риска и безопасности

Пункты 6, 7, 8, 11 из таблицы. Они не про прибыль, а про сохранность денег и
не требуют статистического доказательства: неработающая защита — это дефект,
а не гипотеза.

### Шаг 6 — упрощение score

Только после шага 3, только против baseline, только если проходит ворота
`validation.gate` (три способа из пяти).

## 14. Критерий приёмки

Изменение считается улучшением, только если:

1. не нарушает Risk Manager;
2. не создаёт заглядывания в будущее;
3. не подогнано под один отрезок истории;
4. проходит все существующие проверки;
5. не ухудшает OOS-статистику;
6. улучшает хотя бы одно из: профит-фактор, ожидание, максимальная просадка,
   фактор восстановления — при явно названных ухудшениях остального.

Нет статистического доказательства → статус **UNKNOWN**, а не «улучшение».

**Шаги 1, 2 и 5 — исключение**, и это надо назвать прямо. Они не улучшают
статистику, они чинят дефекты: код, который анализирует несуществующую свечу,
и защита, которая исчезает при перезапуске. Требовать от исправления бага
доказательства роста профит-фактора — значит никогда его не исправить.
